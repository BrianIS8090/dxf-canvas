# Производительность 0.6.1

Проверено 4 сентября 2026 года на Windows x64, Rust 1.97.1, оптимизированная сборка `--release`. Тестовый DXF после преобразования из DWG: 40,3 МБ, 168 слоёв, 113 151 геометрический примитив, 337 текстов, 735 заливок. Производственный файл не входит в репозиторий.

## Результат

Замеряется работа процессора: подготовка изображения и преобразование фигур в треугольники для отрисовки. Это **не полное время кадра приложения и не измерение FPS**: работа видеокарты, оконной системы, боковой панели и проверка проблемных участков в этот замер не входят.

| Сценарий | До оптимизации | 0.6.1 |
| --- | ---: | ---: |
| Общий вид, изменение масштаба: медиана времени кадра | 45–47 мс | 16,48–16,71 мс |
| Поиск привязки у курсора в том же сценарии | около 10,5 мс | около 0,07 мс |
| Общий вид, перемещение: медиана времени кадра | отдельно не измерялось | 16,58 мс |
| Фрагмент чертежа, приближение ×4: медиана времени кадра | отдельно не измерялось | 3,49 мс |

После четырёх прогревочных кадров собираются 20 измерений. Для общего вида выполнены три последовательных запуска, для перемещения и фрагмента — по одному. 95-й процентиль (время, в которое укладываются примерно 95% кадров) общего вида: 17,32–18,27 мс; фрагмента: 5,43 мс. Загрузка и подготовка файла в последних пяти запусках занимала 0,75–0,76 с.

Подготовка общего вида ускорилась примерно в 2,7 раза. Поиск привязки в проверенной позиции — примерно в 150 раз; в плотных местах результат может отличаться. Начальный замер сделан на той же поддержке слоёв и сущностей, до оптимизаций, а не на старой версии, которая пропускала часть содержимого.

Порог 60 кадров/с соответствует 16,67 мс на **весь** кадр. Тест проверяет более узкую часть работы, и один из трёх итоговых запусков общего вида немного превысил даже этот порог. Поэтому стабильные 60 FPS на любом масштабе или компьютере не заявляются.

## Что изменено

- Исправлено застревание дробных штрихов из-за округления чисел: на некоторых масштабах создавались тысячи повторных коротких штрихов либо линия преждевременно обрывалась. Расчёт фазы теперь использует двойную точность. Невидимые части длинных линий пропускаются с сохранением рисунка штрихов.
- Для сложных кривых заранее подготовлены экранные уровни детализации. Дополнительное отклонение этого упрощения ограничено 0,2 физического пикселя; при приближении выбирается более подробный уровень или исходная геометрия. Полные точные окружности рисуются штатным адаптивным примитивом окружности. Рисунок штриховых кривых рассчитывается по исходным точкам.
- Пространственные индексы (деревья габаритов объектов) отбирают кандидатов рядом с курсором и в небольшом видимом фрагменте. На общем виде используется линейный проход, чтобы не платить за сортировку почти всех объектов.
- Соседние прямые передаются на отрисовку группами с сохранением порядка, цвета, толщины и сглаживания. Остальные фигуры также добавляются в список групповой операцией.

Индексы и экранные уровни строятся при загрузке. Перемещение, масштабирование детали и переключение слоёв не перестраивают их. Измерения, нормальная привязка и диагностика используют исходную геометрию; ускорение отображения не округляет измеряемые размеры и не меняет DXF.

Новые сторонние зависимости для этого ускорения не добавлены.

## Повторение замера

Из папки проекта в PowerShell, после сборки и без параллельной компиляции:

```powershell
cargo build --release --example benchmark_canvas
$fixture = 'C:\DXF\reference.dxf'
.\target\release\examples\benchmark_canvas.exe $fixture all zoom
.\target\release\examples\benchmark_canvas.exe $fixture all pan
.\target\release\examples\benchmark_canvas.exe $fixture all detail
```

Замените `$fixture` на путь к своему файлу. Используется область 2200 × 1200 логических пикселей с исходным масштабом, вписывающим чертёж в 2100 × 1100. Сценарий `zoom` меняет масштаб от ×1 до ×1,275 и смещает вид; `pan` сохраняет масштаб; `detail` приближает нижнюю часть чертежа в четыре раза. Шрифты в этом тесте стандартные egui, в Windows-приложении может использоваться системный шрифт.

Тест выводит загрузку, медиану и 95-й процентиль времени кадра, время поиска привязки и количество вершин. Код выхода `2` и `SLOW` означают превышение целевого бюджета: медиана кадра больше 16,67 мс, 95-й процентиль больше 25 мс или медиана поиска привязки больше 2 мс. Это ориентир производительности конкретного компьютера, а не ошибка чтения DXF.

## Защита от регрессий

```powershell
cargo test
cargo clippy --all-targets -- -D warnings
$env:DXF_REFERENCE_FIXTURE = $fixture
cargo test --release reference_drawing_has_no_missing_entities -- --ignored --nocapture
```

Последняя команда предназначена для конкретного большого эталона с указанными выше характеристиками; для другого DXF ожидаемые количества объектов нужно задавать отдельно. Без этого файла тест по умолчанию пропускается.

Синтетические тесты проверяют дробные штрихи, сохранение фазы при обрезке, предел экранного упрощения, совпадение ускоренных привязок с полным поиском после перемещения/масштабирования/переключения слоёв, а также совпадение сглаживания групп прямых при разных масштабах интерфейса. Проверка эталона подтверждает отсутствие пропущенных сущностей. В окне приложения дополнительно проверены приближение, отключение всех слоёв и возврат к исходной видимости.

## Оставшиеся ограничения

Загрузка файла и запуск проверки проблемных участков пока могут приостанавливать интерфейс: в 0.6.1 ускорялись прежде всего навигация и привязки. Плотные видимые штриховки, многочисленные тексты и большие заливки по-прежнему требуют работы на каждом кадре. Результаты одного DXF не гарантируют ту же скорость на всех чертежах; общие ограничения чтения описаны в [матрице поддержки](DXF_SUPPORT.md).

Дополнение 0.6.2: загрузка и подготовка нового файла перенесены в фоновый поток с индикатором. Если диагностика уже включена, отчёт нового файла также готовится в этом потоке. Отдельное нажатие «Проверка DXF» для уже открытых файлов пока выполняет анализ в потоке интерфейса.
