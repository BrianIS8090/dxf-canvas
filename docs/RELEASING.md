# Порядок выпуска

## Обычная проверка изменений

Предложение изменений → автоматические проверки на Windows → проверка интерфейса вручную → включение в `main` → версия и тег → черновик релиза → публикация.

GitHub Actions запускает форматирование, сборку встроенного DWG-конвертера, публичные тесты, Clippy, сборку EXE и установщика при изменениях `main`/`dev`, в предложениях изменений и по тегам `v*`. Установщик проверяется с отдельным именем приложения: установка, восстановление повреждённого EXE, регистрация форматов, ярлыки, удаление и сохранение существующего выбора программ пользователя. Частные эталоны не используются. Версии действий закреплены идентификаторами коммитов; обычная сборка имеет только право чтения. Право записи выделено отдельному шагу подготовки релиза.

## Новый релиз

1. Обновите версию в `Cargo.toml` и выполните `cargo check`, чтобы обновить `Cargo.lock`.
2. Добавьте запись в `CHANGELOG.md` и описание `docs/releases/vX.Y.Z.md`. При изменении интерфейса обновите скриншоты.
3. Проверьте приложение вручную и убедитесь, что автоматические проверки проходят.
4. Зафиксируйте изменения, отправьте их, затем создайте аннотированный тег той же версии и отправьте его:

   ```powershell
   git tag -a vX.Y.Z -m "DXF Холст X.Y.Z"
   git push origin vX.Y.Z
   ```

5. Дождитесь успешной сборки. Она создаст **черновик** GitHub Release с переносимым EXE, установщиком, `SHA256SUMS.txt`, `SIGNING.json` и `THIRD-PARTY-LICENSES.txt`.
6. Проверьте описание и файл, затем **опубликуйте** черновик в разделе Releases или командой `gh release edit vX.Y.Z --draft=false --latest`. Черновик не виден обычным посетителям и не считается завершённым выпуском. Старые релизы и теги не перезаписывайте.

Для первого публичного выпуска 0.5.3 допускается загрузка локально проверенного EXE; последующие теги используют тот же формат файлов. Тег обязан совпадать с версией в `Cargo.toml`.

## Упаковка локальной сборки

```powershell
./scripts/build-dwg-converter.ps1
cargo build --locked --release
./scripts/package-release.ps1
```

Нужен Inno Setup 6 (`C:\Program Files (x86)\Inno Setup 6\ISCC.exe`) или полный путь в `DXF_ISCC`. В `dist/release` появятся `DXF-Canvas-X.Y.Z-windows-x64.exe`, `DXF-Canvas-X.Y.Z-setup-x64.exe`, `SHA256SUMS.txt`, `SIGNING.json` и `THIRD-PARTY-LICENSES.txt`. Лицензии также встроены в сам EXE. Каталог `dist` не хранится в Git: исполняемые файлы размещаются в Releases, а не в истории исходников.

Проверка установщика: `./scripts/verify-installer.ps1`. Отчёт сохраняется в `test-output/installer/results.json`. Посторонние чертежи и настройки при удалении не стираются. Рабочие окна приложение не закрывает автоматически.

Для подписанного выпуска сначала подключите сертификат по [SIGNING.md](SIGNING.md). Стандартный общедоступный процесс GitHub пока выпускает неподписанные файлы. Подпись не считается настроенной до проверки реального сертификата на выбранном исполнителе сборки.

## Проверка обновлений

Приложение запрашивает `https://api.github.com/repos/BrianIS8090/dxf-canvas/releases/latest` по HTTPS с проверкой TLS, ограничением времени 15 секунд и размера ответа 256 КиБ. Проверяются числовая версия, отсутствие признака предварительного выпуска, готовый установщик и точное соответствие адреса нашему репозиторию. Черновики и предварительные версии не предлагаются.

Чтобы версия была видна программе, опубликуйте релиз с установщиком указанного формата и назначьте его последним стабильным выпуском. Не используйте перенаправления на другой репозиторий. Сетевой тест можно вызвать отдельно: `cargo test updates::tests::live_release_check -- --ignored`.

## Проверка скачанного EXE

Откройте PowerShell в папке скачанного файла:

```powershell
Get-FileHash -LiteralPath './DXF-Canvas-0.9.8-windows-x64.exe' -Algorithm SHA256
```

Сравните значение `Hash` с записью из `SHA256SUMS.txt` того же релиза. Контрольная сумма помогает проверить целостность файла, но не заменяет цифровую подпись.
